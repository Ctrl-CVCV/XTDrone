# 空地协同系统启动与应用说明

本文档对应当前仿真工程：两架 `iris` 无人机、三辆无人车和同一个 `nesting_room` Gazebo 世界。

## 1. 系统组成

| 对象 | 名称 | 规划/控制方式 |
|---|---|---|
| 无人机 1 | `iris_0` | PX4 + MAVROS + EGO-Swarm + XTDrone 通信桥 |
| 无人机 2 | `iris_1` | PX4 + MAVROS + EGO-Swarm + XTDrone 通信桥 |
| 防御车 1 | `car0` | AMCL + `nav_to_pose` |
| 防御车 2 | `car1` | AMCL + `nav_to_pose` |
| 入侵车 | `car2` | AMCL + `nav_to_pose` |

统一入口文件：

```text
/home/dev/PX4-Autopilot/launch/multi_vehicle.launch
```

当前出生点（Gazebo 世界坐标）：

```text
iris_0 = (-2.3,  2.3)
iris_1 = ( 2.3, -2.3)
car0   = ( 2.3,  2.4)
car1   = (-2.3, -2.4)
car2   = (-6.5,  6.6)
```

小房间内墙边界约为：

```text
x: -3.166 ～ 2.934
y: -3.059 ～ 3.041
```

## 2. 坐标系说明

这是发布目标点前最需要注意的地方。

- 三辆车的目标使用全局 `map` 坐标，基本等于 Gazebo 世界坐标。
- 每架 PX4 无人机的 MAVROS local 坐标都以自己的出生点为原点。
- 两架无人机的话题都可能标记为 `map`，但它们的数值并不是同一个全局原点。

无人机目标换算公式：

```text
无人机本地目标 = Gazebo 世界目标 - 无人机 Gazebo 出生点
```

例如，让两架无人机飞向不同的世界坐标：

```text
iris_0 世界目标 ( 1.5, -1.5, 1.5)
iris_0 本地目标 ( 3.8, -3.8, 1.5)

iris_1 世界目标 (-1.5,  1.5, 1.5)
iris_1 本地目标 (-3.8,  3.8, 1.5)
```

不要把 `iris_0` 的出生坐标 `(-2.3, 2.3)` 直接发布到它的 MAVROS local setpoint；那表示从出生点再偏移 `(-2.3, 2.3)`。

## 3. 完整启动顺序

建议使用多个终端，并在每个终端先执行：

```bash
source /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/devel/setup.bash
```

这个最上层工作空间已经叠加了 `ego_ws` 和 `catkin_ws`。如果没有加载它，ROS 会提示找不到 `basic_room_sim` 或 `car3_swarm`。

### 3.1 启动统一 Gazebo、两机三车、Nav 和 EGO

终端 1：

```bash
source /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/devel/setup.bash

roslaunch px4 multi_vehicle.launch \
  gui:=true \
  start_car_nav:=true \
  start_ego:=true
```

等待 Gazebo 完成模型加载。检查模型：

```bash
rosservice call /gazebo/get_world_properties
```

应至少包含：

```text
nesting_room
iris_0
iris_1
car0
car1
car2
```

检查两套 MAVROS：

```bash
rostopic echo -n 1 /iris_0/mavros/state
rostopic echo -n 1 /iris_1/mavros/state
```

两个结果都应为：

```text
connected: True
```

### 3.2 启动 Gazebo ground-truth 位姿输入

无人机定位直接使用 Gazebo 真实位姿，并通过 MAVROS vision pose/speed 输入 PX4 EKF。

统一仿真启动并生成两架 Iris 后，在独立的终端 2 执行：

```bash
source /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/devel/setup.bash
cd /home/dev/XTDrone/sensing/pose_ground_truth
python3 get_local_pose.py iris 2
```

参数含义：

- `iris`：车辆类型；
- `2`：无人机数量，脚本处理 `iris_0` 和 `iris_1`。

该脚本的数据链为：

```text
/gazebo/model_states
        ↓
/iris_0/mavros/vision_pose/pose
/iris_0/mavros/vision_speed/speed
/iris_1/mavros/vision_pose/pose
/iris_1/mavros/vision_speed/speed
        ↓
PX4 EKF / MAVROS local_position
```

保持该终端运行，并检查两架飞机均以约 `30 Hz` 收到真实位姿：

```bash
rostopic hz /iris_0/mavros/vision_pose/pose
rostopic hz /iris_1/mavros/vision_pose/pose
rostopic hz /iris_0/mavros/local_position/odom
rostopic hz /iris_1/mavros/local_position/odom
```

保持 ground-truth 位姿终端运行，然后执行第 3.3 节的 EGO-Swarm 位姿转换。

### 3.3 启动 EGO-Swarm 位姿转换

在独立的终端 3 执行：

```bash
source /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/devel/setup.bash
cd /home/dev/XTDrone/motion_planning/3d
python3 ego_swarm_transfer.py iris 2
```

该脚本同时处理 `iris_0`、`iris_1`，完成：

```text
/iris_N/mavros/local_position/pose
        ↓
/iris_N/camera_pose
```

保持该终端运行，并检查：

```bash
rostopic hz /iris_0/camera_pose
rostopic hz /iris_1/camera_pose
```

两架飞机的 `camera_pose` 正常发布后，才能建立多机通信并执行下一节的一键起飞。

### 3.4 一键启动通信桥、OFFBOARD、ARM 和起飞

终端 4：

```bash
source /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/devel/setup.bash

rosrun car3_swarm uav_offboard_takeoff.py --altitude 1.5
```

脚本会依次完成：

1. 检查两架飞机的 Gazebo ground-truth `vision_pose` 已经发布；
2. 检查 `ego_swarm_transfer.py iris 2` 已为两架飞机发布 `camera_pose`；
3. 等待 `iris_0`、`iris_1` 的 MAVROS connected 和 local pose；
4. 检查 XTDrone 通信桥，缺失时自动启动；
5. 发送 `HOVER` 并确认两套 setpoint 持续发布；
6. 将两架飞机切换到 `OFFBOARD`；
7. 将两架飞机 ARM；
8. 让两架飞机在各自出生点原地上升至 `1.5 m`；
9. 保持自动启动的通信桥运行，等待 EGO 目标。

成功时显示：

```text
成功：iris_0、iris_1 均已 OFFBOARD、ARM，并到达起飞高度
```

修改起飞高度：

```bash
rosrun car3_swarm uav_offboard_takeoff.py --altitude 1.2
```

如果通信桥已经运行，脚本会直接复用。只有明确不希望脚本自动启动通信桥时才使用：

```bash
rosrun car3_swarm uav_offboard_takeoff.py --altitude 1.5 --no-start-bridge
```

该终端应保持运行。若通信桥由脚本启动，在飞机仍处于 OFFBOARD 时按 `Ctrl+C` 会中断通信桥，因此必须先降落并解除武装。

### 3.5 启动联合 RViz

终端 5：

```bash
source /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/devel/setup.bash
rviz -d /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/src/car3_swarm/rviz/air_ground.rviz
```

RViz 中：

- `iris_0` 显示为黄色 Pose 箭头；
- `iris_1` 显示为紫色 Pose 箭头；
- 两个箭头使用 Gazebo 世界坐标，不再使用会重叠的 MAVROS local 原点；
- 不加载无人机真实网格模型。

对应话题：

```text
/air_ground/iris_0/world_pose
/air_ground/iris_1/world_pose
```

位姿发布节点 `uav_rviz_state.py` 已由统一 `multi_vehicle.launch` 自动启动。

## 5. 手动切换与起飞（仅用于排查）

正常使用应执行第 3.4 节的一键脚本。仅当脚本失败、需要分步定位问题时，才手动操作。

先手动启动通信桥：

```bash
cd /home/dev/XTDrone/communication
bash multi_vehicle_communication.sh
```

确认两套 setpoint 约为 `30 Hz` 后，依次执行：

```bash
rostopic pub -1 /xtdrone/iris_0/cmd std_msgs/String "data: HOVER"
rostopic pub -1 /xtdrone/iris_1/cmd std_msgs/String "data: HOVER"

rostopic pub -1 /xtdrone/iris_0/cmd std_msgs/String "data: OFFBOARD"
rostopic pub -1 /xtdrone/iris_1/cmd std_msgs/String "data: OFFBOARD"

rostopic pub -1 /xtdrone/iris_0/cmd std_msgs/String "data: ARM"
rostopic pub -1 /xtdrone/iris_1/cmd std_msgs/String "data: ARM"
```

最后发布本地 ENU 起飞点。两架飞机的本地出生点均约为 `(0,0,0)`：

```bash
rostopic pub -1 /xtdrone/iris_0/cmd_pose_enu geometry_msgs/Pose "{position: {x: 0.0, y: 0.0, z: 1.5}, orientation: {w: 1.0}}"

rostopic pub -1 /xtdrone/iris_1/cmd_pose_enu geometry_msgs/Pose "{position: {x: 0.0, y: 0.0, z: 1.5}, orientation: {w: 1.0}}"
```

## 6. 给 EGO-Swarm 发布无人机目标点

EGO 目标话题：

```text
/iris_0/move_base_simple/goal
/iris_1/move_base_simple/goal
```

消息类型均为 `geometry_msgs/PoseStamped`。目标坐标使用该飞机的 MAVROS 本地坐标。

示例：让两架飞机飞向小房间内不同位置，高度均为 `1.5 m`：

```bash
rostopic pub -1 /iris_0/move_base_simple/goal geometry_msgs/PoseStamped \
"{header: {frame_id: 'map'}, pose: {position: {x: 3.8, y: -3.8, z: 1.5}, orientation: {w: 1.0}}}"

rostopic pub -1 /iris_1/move_base_simple/goal geometry_msgs/PoseStamped \
"{header: {frame_id: 'map'}, pose: {position: {x: -3.8, y: 3.8, z: 1.5}, orientation: {w: 1.0}}}"
```

这两个本地目标分别对应约以下 Gazebo 世界目标：

```text
iris_0 -> ( 1.5, -1.5, 1.5)
iris_1 -> (-1.5,  1.5, 1.5)
```

检查 EGO 是否生成控制输出：

```bash
rostopic hz /xtdrone/iris_0/planning/pos_cmd
rostopic hz /xtdrone/iris_1/planning/pos_cmd

rostopic hz /xtdrone/iris_0/cmd_pose_enu
rostopic hz /xtdrone/iris_1/cmd_pose_enu
```

其中 `traj_server` 会把 EGO 轨迹转换为 `/xtdrone/iris_N/cmd_pose_enu`，再由通信桥发送给 PX4。

## 7. 给三辆车发布 Nav 目标点

车辆目标话题：

```text
/car0/move_base_simple/goal
/car1/move_base_simple/goal
/car2/move_base_simple/goal
```

车辆使用全局地图坐标，不需要减去出生点。

示例：

```bash
rostopic pub -1 /car0/move_base_simple/goal geometry_msgs/PoseStamped \
"{header: {frame_id: 'map'}, pose: {position: {x: 0.0, y: -1.5, z: 0.0}, orientation: {w: 1.0}}}"

rostopic pub -1 /car1/move_base_simple/goal geometry_msgs/PoseStamped \
"{header: {frame_id: 'map'}, pose: {position: {x: -1.0, y: -0.5, z: 0.0}, orientation: {w: 1.0}}}"

rostopic pub -1 /car2/move_base_simple/goal geometry_msgs/PoseStamped \
"{header: {frame_id: 'map'}, pose: {position: {x: -2.5, y: -1.0, z: 0.0}, orientation: {w: 1.0}}}"
```

`orientation.w: 1.0` 表示目标偏航角为 `0 rad`。如果需要指定目标朝向，应把 yaw 转换为四元数。

## 8. 一条命令发布四组空地目标

脚本一次控制 `iris_0`、`iris_1`、`car0`、`car1`；`car2` 是 intruder，不包含在这四组目标中。

调用格式：

```bash
rosrun car3_swarm send_air_ground_goals.py --iris0 X Y Z --iris1 X Y Z --car0 X Y --car1 X Y
```

四组参数全部使用 Gazebo/地图世界坐标。脚本会根据 `/gazebo/model_states` 和 MAVROS local pose，自动将两架无人机的世界目标换算成各自 EGO 本地目标；车辆目标直接使用全局 `map` 坐标。

示例：

```bash
source /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/devel/setup.bash
rosrun car3_swarm send_air_ground_goals.py --iris0 1.5 -1.5 1.5 --iris1 -1.5 1.5 1.5 --car0 0.0 -1.5 --car1 -1.0 -0.5
```

只换算、不发布：

```bash
rosrun car3_swarm send_air_ground_goals.py --iris0 1.5 -1.5 1.5 --iris1 -1.5 1.5 1.5 --car0 0.0 -1.5 --car1 -1.0 -0.5 --dry-run
```

正式发布前必须确保两套 EGO 和 `car0/car1` Nav 都在线。脚本会等待四个目标话题均有订阅者后再发布。

## 9. 一次空地协同任务的推荐操作流程

1. 启动统一 `multi_vehicle.launch`。
2. 确认 Gazebo 中存在两机三车，且两套 MAVROS connected。
3. 启动 `get_local_pose.py iris 2`，确认两架飞机的 vision pose 和 local odom 正常。
4. 启动 `ego_swarm_transfer.py iris 2`，确认两架飞机的 camera pose 正常。
5. 启动联合 RViz。
6. 运行 `uav_offboard_takeoff.py --altitude 1.5`。
7. 等待终端报告两机均已 OFFBOARD、ARM 并到达起飞高度。
8. 使用 `send_air_ground_goals.py` 一次发布两机、两辆 defender 的四组目标。
9. 如需控制 intruder，再单独向 `/car2/move_base_simple/goal` 发布目标。
10. 在 Gazebo、RViz 和状态话题中观察执行情况。
11. 任务结束后先降落、DISARM，再结束一键起飞脚本和统一仿真。

## 10. 悬停、降落和解除武装

让 EGO 轨迹停止后保持当前位置：

```bash
rostopic pub -1 /xtdrone/iris_0/cmd std_msgs/String "data: 'HOVER'"
rostopic pub -1 /xtdrone/iris_1/cmd std_msgs/String "data: 'HOVER'"
```

请求 PX4 自动降落：

```bash
rostopic pub -1 /xtdrone/iris_0/cmd std_msgs/String "data: 'AUTO.LAND'"
rostopic pub -1 /xtdrone/iris_1/cmd std_msgs/String "data: 'AUTO.LAND'"
```

确认飞机已经落地后再解除武装：

```bash
rostopic pub -1 /xtdrone/iris_0/cmd std_msgs/String "data: 'DISARM'"
rostopic pub -1 /xtdrone/iris_1/cmd std_msgs/String "data: 'DISARM'"
```

不要在空中直接 `DISARM`。

## 11. 常见问题

### 11.1 找不到 `basic_room_sim`

```bash
source /home/dev/XTDrone-single-car/workspace/swarm_defense_ws/devel/setup.bash
rospack find basic_room_sim
```

### 11.2 PX4 无法进入 OFFBOARD

依次检查：

```bash
rostopic echo -n 1 /iris_0/mavros/state
rostopic hz /iris_0/mavros/setpoint_raw/local
```

必须满足：

- MAVROS `connected: True`；
- 切换前已经连续发送 setpoint；
- setpoint 频率高于 `2 Hz`，当前通信桥应约为 `30 Hz`；
- 切换后 setpoint 不能中断。

### 11.3 ARM 失败

检查 PX4 控制台中的 preflight 报错、MAVROS 连接和 OFFBOARD 状态。如果仿真无 RC，确认两机的 `COM_RCL_EXCEPT` 已设为 `4`。

查询参数：

```bash
rosservice call /iris_0/mavros/param/get "param_id: 'COM_RCL_EXCEPT'"
rosservice call /iris_1/mavros/param/get "param_id: 'COM_RCL_EXCEPT'"
```

### 11.4 EGO 一直显示 `no odom`

按完整位姿链逐级检查：

```bash
rostopic hz /gazebo/model_states
rostopic hz /iris_0/mavros/vision_pose/pose
rostopic hz /iris_1/mavros/vision_pose/pose
rostopic hz /iris_0/mavros/local_position/odom
rostopic hz /iris_1/mavros/local_position/odom
rostopic hz /iris_0/camera_pose
rostopic hz /iris_1/camera_pose
```

- `/gazebo/model_states` 正常但 `vision_pose` 没有数据：`get_local_pose.py iris 2` 未运行或已退出；
- `vision_pose` 正常但 `local_position/odom` 没有数据：检查 PX4 EKF 和 MAVROS；
- `local_position/odom` 正常但 `camera_pose` 没有数据：`ego_swarm_transfer.py iris 2` 未运行或已退出。

### 11.5 EGO 有轨迹但飞机不动

按顺序检查：

```bash
rostopic hz /xtdrone/iris_0/planning/pos_cmd
rostopic hz /xtdrone/iris_0/cmd_pose_enu
rostopic hz /iris_0/mavros/setpoint_raw/local
rostopic echo -n 1 /iris_0/mavros/state
```

最常见原因是 XTDrone 通信桥未运行，或者飞机不在 `OFFBOARD`/未 ARM。

### 11.6 RViz 中没有 Iris 或两架飞机重叠

当前联合 RViz 不加载真实无人机模型，而是显示两个世界坐标 Pose 箭头：

```text
/air_ground/iris_0/world_pose
/air_ground/iris_1/world_pose
```

检查话题：

```bash
rostopic echo -n 1 /air_ground/iris_0/world_pose
rostopic echo -n 1 /air_ground/iris_1/world_pose
rosnode info /uav_rviz_state
```

如果没有话题，说明当前仿真仍是修改前启动的旧 launch；重新启动 `multi_vehicle.launch`。如果话题正常但 RViz 不显示，关闭旧 RViz 并用第 3.5 节命令重新加载配置。

### 11.7 控制话题互相抢占

同一时刻只能有一条控制链持续给 MAVROS 发布 setpoint。使用 EGO 时保留 XTDrone 通信桥，但不要再运行会持续直接发布 `/iris_N/mavros/setpoint_position/local` 的其他脚本。

当前 `air_ground_unified_control.py` 在末尾持续发布起飞 position setpoint，可能覆盖 EGO 经通信桥产生的轨迹。因此按本文档手动运行 EGO 时，不要同时运行该脚本。

## 12. 关闭顺序

1. 停止继续发布新目标。
2. 两架飞机执行 `HOVER` 或 `AUTO.LAND`。
3. 确认落地后执行 `DISARM`。
4. 再在一键起飞脚本终端按 `Ctrl+C`；若通信桥由脚本启动，此时会一并关闭。
5. 停止 `ego_swarm_transfer.py iris 2`。
6. 停止 `get_local_pose.py iris 2`。
7. 关闭 RViz。
8. 最后在统一 `roslaunch` 终端按 `Ctrl+C`，等待 Gazebo、PX4 和 ROS 节点完整退出。

## 14. 暂停、恢复与进程冲突清理

### 14.1 只暂停/恢复 Gazebo 仿真时间

暂停后所有 ROS 节点仍然保留，只是 Gazebo 的物理时间停止，适合临时观察现场：

```bash
rosservice call /gazebo/pause_physics "{}"
```

恢复：

```bash
rosservice call /gazebo/unpause_physics "{}"
```

这不会解决重复 launch 或同名节点冲突。

### 14.2 只暂停协同追捕

先让两架无人机锁定当前位置，再停止追捕节点：

```bash
rostopic pub -1 /xtdrone/iris_0/cmd std_msgs/String "data: 'HOVER'"
rostopic pub -1 /xtdrone/iris_1/cmd std_msgs/String "data: 'HOVER'"
rosnode kill /voronoi_air_ground_pursuit
```

统一 Gazebo、PX4、MAVROS、Nav、EGO、ground-truth 和 transfer 会继续运行。重新启动追捕时执行：

```bash
roslaunch car3_swarm voronoi_air_ground_pursuit.launch \
  return_delay:=1.0 \
  return_tolerance:=0.50
```

如果该命令显示 `auto-starting new master`，说明统一仿真已经不在线。立即按 `Ctrl+C`，不要在这个空 Master 上继续运行追捕。

### 14.3 一键正常停止全部相关进程

遇到以下现象时使用：

- `Reason: new node registered with same name`；
- `No ROS master` 或大量 XML-RPC `Connection refused`；
- Gazebo 中模型重复、缺失；
- `pgrep` 显示多份 `multi_vehicle.launch`。

可以把下面整段一次性粘贴到一个终端。它只匹配本项目的明确进程，不会执行 `killall python3`：

```bash
pkill -INT -f '[/]voronoi_air_ground_pursuit.py'
pkill -INT -f '[/]uav_offboard_takeoff.py'
pkill -INT -f '[/]multirotor_communication.py iris [01]'
pkill -INT -f '[/]ego_swarm_transfer.py iris 2'
pkill -INT -f '[/]get_local_pose.py iris 2'
pkill -INT -f '[/]roslaunch px4 multi_vehicle.launch'

sleep 10

pgrep -af 'roslaunch px4 multi_vehicle.launch|rosmaster|gzserver|gzclient|get_local_pose.py|ego_swarm_transfer.py|uav_offboard_takeoff.py|multirotor_communication.py|voronoi_air_ground_pursuit.py'
```

正常情况下，最后一条 `pgrep` 不应显示活动进程。显示 `<defunct>` 或状态 `Z` 的 Gazebo 进程只是由 PID 1 尚未回收的僵尸，不消耗实际 CPU，也无法再通过 `kill` 清除。

只有等待 10 秒后仍有非 `Z` 的明确残留进程时，才执行第二阶段：

```bash
pkill -TERM -f '[/]voronoi_air_ground_pursuit.py'
pkill -TERM -f '[/]uav_offboard_takeoff.py'
pkill -TERM -f '[/]multirotor_communication.py iris [01]'
pkill -TERM -f '[/]ego_swarm_transfer.py iris 2'
pkill -TERM -f '[/]get_local_pose.py iris 2'
pkill -TERM -f '[/]roslaunch px4 multi_vehicle.launch'
pkill -TERM -f '[/]gzserver .*nesting_room.world'
```

清理后必须按“统一仿真 → ground-truth → transfer → 一键起飞 → 追捕”的顺序重新启动。启动统一仿真前先检查：

```bash
pgrep -af 'roslaunch px4 multi_vehicle.launch'
```

没有输出才可以启动；启动后应始终只有一份结果。

## 15. 中央云台与单双入侵模式

统一仿真使用的 `nesting_room.world` 已在小房间中心加入固定云台：

```text
模型名：camera_gimbal
坐标：(-0.11576, -0.00882, 0.02)
图像：/gimbal_camera/image_raw
内参：/gimbal_camera/camera_info
```

云台模型设为 `static`，启动统一仿真后自动随 world 加载，不需要再运行 `camera_urdf/reload.sh`。验证命令：

```bash
rosservice call /gazebo/get_world_properties | grep camera_gimbal
rostopic hz /gimbal_camera/image_raw
```

围捕任务默认使用双车入侵。根据实验需要，在最后启动追捕节点时二选一：

```bash
# 单车入侵：只追捕 car2
roslaunch car3_swarm voronoi_air_ground_pursuit.launch intruder_mode:=single

# 双车入侵：同时追捕 car2、car3
roslaunch car3_swarm voronoi_air_ground_pursuit.launch intruder_mode:=dual
```

`single` 模式不会控制或等待 `car3`，捕获 `car2` 后立即返航；`dual` 模式在两辆入侵车都被捕获后返航。切换模式只需先停止 `/voronoi_air_ground_pursuit` 再重新执行对应命令，不需要重新启动统一 Gazebo。

## 16. EGO-Swarm 四面虚拟边界墙

由于当前 EGO 不使用深度相机建图，原来的 `/iris_N/pcl_render_node/points` 没有发布者，规划器并不知道小房间墙体的位置。统一 launch 现在会在 `start_ego:=true` 时自动启动 `/ego_virtual_boundary`，把 6 m 正方形边界转换到每架飞机的 MAVROS 本地坐标，并发布为 EGO 障碍点云：

```text
/iris_0/pcl_render_node/points
/iris_1/pcl_render_node/points
```

四面墙范围为：

```text
x = [-3.11576, 2.88424]
y = [-3.00882, 2.99118]
z = [0.0, 3.0]
点间距 = 0.3 m
EGO 障碍膨胀 = 0.2 m
```

同时，EGO 栅格 odom 已从没有发布者的 `/xtdrone/iris_N/.../odom` 修正为实际的 `/iris_N/mavros/local_position/odom`。修改后必须重新启动 `multi_vehicle.launch`，仅重启追捕节点不会更新 EGO 的 remap。

正常启动无需增加参数：

```bash
roslaunch px4 multi_vehicle.launch gui:=true start_car_nav:=true start_ego:=true
```

临时禁用虚拟墙：

```bash
roslaunch px4 multi_vehicle.launch \
  gui:=true start_car_nav:=true start_ego:=true \
  use_ego_virtual_boundary:=false
```

调整墙高或点间距：

```bash
roslaunch px4 multi_vehicle.launch \
  gui:=true start_car_nav:=true start_ego:=true \
  ego_boundary_z_max:=3.0 \
ego_boundary_spacing:=0.3
```

验证：

```bash
rosnode info /ego_virtual_boundary
rostopic info /iris_0/pcl_render_node/points
rostopic info /iris_1/pcl_render_node/points
rostopic hz /iris_0/pcl_render_node/points
rostopic hz /iris_1/pcl_render_node/points
```

节点会等待两套 EGO 连接和两机本地原点稳定，然后分别发布一次锁存点云；确认送达后自动退出，不再持续重建占据栅格或占用 CPU。因此任务稳定运行时 `rosnode list` 中没有 `/ego_virtual_boundary` 是正常现象。启动日志应出现两条 `published once` 和一条 `node exits`。

虚拟墙约束的是 EGO 的整条轨迹；`target_margin` 仍用于把围捕目标点从边界向内收缩，两者用途不同。如果运行中单独重启了 EGO 节点，其内存地图会丢失，此时需要手动重新注入一次：

```bash
rosrun car3_swarm ego_virtual_boundary.py _spacing:=0.3
```
